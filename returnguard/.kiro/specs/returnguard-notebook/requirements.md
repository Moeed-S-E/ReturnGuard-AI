# Requirements Document

## Introduction

ReturnGuard Notebook is a self-contained Jupyter notebook that serves as the first-step prototype for an explainable AI return-abuse detection system. The notebook ingests an e-commerce returns dataset (~60,000 rows, 4-class target `abuse_type`), performs exploratory data analysis, engineers risk-relevant features, trains a LightGBM multiclass classifier with auto-tuned thresholds, explains predictions with SHAP waterfall plots (one per class), and exposes a `predict_return()` policy engine function. The notebook is the foundation for later conversion to modular `.py` files and a Streamlit UI.

## Glossary

- **Notebook**: The single Jupyter `.ipynb` file being built, located at `returnguard/returnguard_prototype.ipynb`.
- **Dataset**: The CSV file at `datasets/ecommerce_return_abuse_dataset.csv`, approximately 60,000 rows.
- **abuse_type**: The 4-class target column with values: `Legitimate`, `Policy Abuser`, `Fraudulent Return`, `Wardrobing`.
- **abuse_label**: The integer-encoded version of `abuse_type` (0–3).
- **LightGBM Model**: A LightGBM `LGBMClassifier` configured for multiclass classification.
- **TreeExplainer**: The SHAP `TreeExplainer` instance used to compute SHAP values for the trained model.
- **Policy Engine**: The `predict_return()` function that converts model probabilities into a policy action and customer-facing messaging.
- **POLICY_CONFIG**: A single Python dict holding all probability thresholds and fee values used by the Policy Engine.
- **Validation Set**: The 10% stratified split held out from training data, used exclusively for threshold tuning.
- **Test Set**: The 20% stratified split held out for final evaluation; not used during threshold tuning.
- **Demo Profile**: One of four handcrafted feature dicts representing Honest Shopper, Wardrober, Policy Abuser, and Fraudster personas.
- **category_risk_index**: Per-category mean fraud rate computed exclusively from the training split to prevent data leakage.
- **SHAP Waterfall Plot**: A plot generated by `shap.plots.waterfall` showing the contribution of each feature to a single prediction.

## Requirements

### Requirement 1: Dataset Loading and Validation

**User Story:** As a notebook user, I want the dataset loaded and validated at startup, so that subsequent cells operate on confirmed, well-understood data.

#### Acceptance Criteria

1. THE Notebook SHALL load `datasets/ecommerce_return_abuse_dataset.csv` using a relative path resolved from the notebook's parent directory.
2. WHEN the CSV file is not found at the expected path, THE Notebook SHALL raise a `FileNotFoundError` with a message stating the expected path.
3. THE Notebook SHALL display the dataset shape (rows, columns), the `abuse_type` class distribution with counts and percentages, the count of missing values per column, and the data types of all columns.
4. THE Notebook SHALL verify that the `abuse_type` column contains exactly the four values: `Legitimate`, `Policy Abuser`, `Fraudulent Return`, `Wardrobing`, and SHALL raise a `ValueError` if any value is absent.
5. THE Notebook SHALL NOT load `Fraudulent_E-Commerce_Transaction_Data.csv` or `Fraudulent_E-Commerce_Transaction_Data_2.csv` as primary training data.

---

### Requirement 2: Exploratory Data Analysis (EDA)

**User Story:** As a notebook user, I want a structured EDA section, so that I can understand class imbalance, feature distributions, and correlations before modeling.

#### Acceptance Criteria

1. THE Notebook SHALL render a bar chart of `abuse_type` class counts with percentage labels on each bar.
2. THE Notebook SHALL render a heatmap of Pearson correlations among all numeric columns, using a diverging colormap.
3. THE Notebook SHALL display a count or percentage summary of missing values for every column that has at least one missing value.
4. WHEN a numeric column has no missing values, THE Notebook SHALL NOT include that column in the missing-value summary.
5. THE Notebook SHALL display distribution plots (histogram or KDE) for at least the following numeric columns: `days_to_return`, `return_rate_pct`, `avg_order_value_usd`, `refund_amount_requested_usd`, `total_returns_lifetime`.
6. THE Notebook SHALL display a cross-tabulation or grouped bar chart of `abuse_type` against at least two categorical columns: `product_category` and `return_reason`.

---

### Requirement 3: Feature Engineering

**User Story:** As a notebook user, I want five risk-relevant engineered features added to the dataset, so that the model has predictive signals beyond the raw columns.

#### Acceptance Criteria

1. THE Notebook SHALL compute `order_to_return_days` as the integer difference in calendar days between `return_date` and `order_date`, coerced to non-negative values (minimum 0).
2. THE Notebook SHALL compute `return_ratio` as `total_returns_lifetime` divided by `total_orders_lifetime`, with a floor of 1 in the denominator to prevent division by zero.
3. THE Notebook SHALL compute `risk_exposure` as `refund_amount_requested_usd` multiplied by the quantity `(1 + previous_dispute_count)`.
4. THE Notebook SHALL compute `category_risk_index` as the mean fraud-class rate per `product_category`, calculated ONLY on the training split rows, then mapped onto all splits to prevent data leakage.
5. THE Notebook SHALL compute `dispute_frequency` as `previous_dispute_count` divided by the maximum of `(account_age_days / 30)` and `1`.
6. THE Notebook SHALL NOT use `customer_id` or `order_id` as model input features.
7. THE Notebook SHALL print the names of all final model input features in a single list before the train/test split cell.

---

### Requirement 4: Train/Validation/Test Split

**User Story:** As a notebook user, I want a stratified three-way split, so that class distribution is preserved across all data subsets and threshold tuning is done on held-out data.

#### Acceptance Criteria

1. THE Notebook SHALL split the dataset into training (70%), validation (10%), and test (20%) subsets using stratified sampling on `abuse_type`.
2. THE Notebook SHALL set `random_state=42` for all split operations to ensure reproducibility.
3. THE Notebook SHALL print the class distribution (counts and percentages) for each of the three splits after splitting.
4. THE Notebook SHALL compute `category_risk_index` from training rows only and apply the resulting mapping to validation and test rows.

---

### Requirement 5: LightGBM Multiclass Model Training

**User Story:** As a notebook user, I want a trained LightGBM multiclass classifier, so that each return request can be scored across all four abuse classes.

#### Acceptance Criteria

1. THE Notebook SHALL train a `LGBMClassifier` with `objective="multiclass"`, `num_class=4`, `class_weight="balanced"`, and `random_state=42`.
2. THE Notebook SHALL specify all string/categorical columns in the `categorical_feature` parameter, using LightGBM's native categorical support rather than one-hot encoding.
3. WHEN LightGBM native categorical encoding is used, THE Notebook SHALL cast all categorical columns to the pandas `"category"` dtype before passing them to the model.
4. THE Notebook SHALL use early stopping on the validation set with a patience of at least 50 rounds to prevent overfitting.
5. THE Notebook SHALL report the macro F1 score, per-class precision, per-class recall, and confusion matrix on the test set.
6. THE Notebook SHALL save the trained model to `returnguard/artifacts/model.joblib` using `joblib.dump`.
7. THE Notebook SHALL save a `metrics.json` file to `returnguard/artifacts/metrics.json` containing macro F1, per-class F1, and the label-to-integer mapping.
8. IF the `returnguard/artifacts/` directory does not exist, THEN THE Notebook SHALL create it before attempting to save artifacts.

---

### Requirement 6: Probability Threshold Auto-Tuning

**User Story:** As a notebook user, I want the policy thresholds auto-tuned on the validation set, so that the Policy Engine decision boundaries are optimized rather than fixed at PRD starting values.

#### Acceptance Criteria

1. THE Notebook SHALL define a `POLICY_CONFIG` dict containing one probability threshold entry per class: `thresh_legitimate`, `thresh_wardrobing`, `thresh_policy_abuser`, `thresh_fraudulent`.
2. THE Notebook SHALL tune each class threshold on the validation set by sweeping values in the range [0.30, 0.90] in increments of 0.05.
3. WHEN tuning thresholds, THE Notebook SHALL optimize for per-class recall, selecting the threshold that maximizes recall for the minority classes (`Fraudulent Return`, `Wardrobing`, `Policy Abuser`) and precision for `Legitimate`.
4. THE Notebook SHALL print the tuned threshold for each class alongside its achieved validation recall or precision value.
5. THE Notebook SHALL update `POLICY_CONFIG` in-place with the tuned thresholds so all subsequent cells use the auto-tuned values.
6. THE Notebook SHALL evaluate the policy decision rule on the test set — applying severity-ordered evaluation (Fraud → Wardrobing → Abuser → Legitimate → Uncertain) — and report the resulting class-level accuracy.

---

### Requirement 7: SHAP Explainability

**User Story:** As a notebook user, I want four SHAP waterfall plots (one per abuse class), so that I can verify which features drive each class prediction.

#### Acceptance Criteria

1. THE Notebook SHALL create a `shap.TreeExplainer` from the trained LightGBM model after training is complete.
2. THE Notebook SHALL compute SHAP values for the test set using `TreeExplainer.shap_values()`.
3. WHEN the SHAP output is a list (one array per class), THE Notebook SHALL index into the list by class index to obtain per-class SHAP arrays.
4. WHEN the SHAP output is a 3-D numpy array (samples × features × classes), THE Notebook SHALL slice along the last axis to obtain per-class SHAP arrays.
5. THE Notebook SHALL render exactly four `shap.plots.waterfall` plots, one for each of the four classes, each using one representative test-set sample predicted with high confidence (probability >= 0.70) for that class.
6. WHEN no test sample has predicted probability >= 0.70 for a given class, THE Notebook SHALL select the sample with the highest predicted probability for that class.
7. THE Notebook SHALL display a descriptive title above each waterfall plot identifying the class it represents.
8. THE Notebook SHALL NOT call `plt.show()` in a way that suppresses inline rendering in Jupyter.

---

### Requirement 8: Policy Engine Function

**User Story:** As a notebook user, I want a `predict_return()` function that encapsulates the full prediction pipeline, so that the Streamlit UI can call a single function per return request.

#### Acceptance Criteria

1. THE Notebook SHALL define a function `predict_return(features: dict) -> dict` that accepts a dictionary of raw feature values and returns a result dictionary.
2. THE Policy Engine SHALL return a result dict containing: `probs` (dict mapping class name to float probability), `predicted_class` (str), `action` (one of `AUTO_APPROVE`, `VERIFY_TAGS`, `FEE_DEDUCTION`, `FRAUD_HOLD`, `LIGHT_VERIFY`), `fee_pkr` (int, 0 unless action is `FEE_DEDUCTION`), `customer_message` (str), `merchant_note` (str), `top_reasons` (list of (feature_name, shap_value) tuples, length 3), and `latency_ms` (float).
3. THE Policy Engine SHALL evaluate class thresholds in severity order: Fraudulent Return first, Wardrobing second, Policy Abuser third, Legitimate fourth; if no threshold is met, THE Policy Engine SHALL return action `LIGHT_VERIFY`.
4. WHEN action is `FEE_DEDUCTION`, THE Policy Engine SHALL set `fee_pkr` to 950.
5. THE Policy Engine SHALL measure total function latency using `time.perf_counter` and return it as `latency_ms`.
6. THE Policy Engine SHALL use the cached `TreeExplainer` instance (not create a new one per call) to compute `top_reasons`.
7. THE Notebook SHALL include a `POLICY_CONFIG` dict as the single source of truth for all thresholds and the `fee_pkr` value; the Policy Engine function SHALL NOT hardcode threshold values.

---

### Requirement 9: Demo Profile Validation

**User Story:** As a notebook user, I want four preset demo profiles validated against the trained model, so that I can confirm the Policy Engine produces the expected action for each persona before the pitch.

#### Acceptance Criteria

1. THE Notebook SHALL define four demo profile dicts corresponding to: Honest Shopper (expected action `AUTO_APPROVE`), Wardrober (expected action `VERIFY_TAGS`), Policy Abuser (expected action `FEE_DEDUCTION`), and Fraudster (expected action `FRAUD_HOLD`).
2. THE Notebook SHALL call `predict_return()` for each demo profile and display the returned `predicted_class`, `action`, `probs`, and `customer_message`.
3. THE Notebook SHALL print a PASS or FAIL result for each demo profile by comparing the returned `action` against the expected action.
4. WHEN a demo profile returns FAIL, THE Notebook SHALL print the full probability dict to aid diagnosis.
5. THE Notebook SHALL NOT modify model weights or thresholds based on demo profile results; profile feature values may be adjusted in the profile dicts to achieve expected outcomes.

---

### Requirement 10: Notebook Structure and Reproducibility

**User Story:** As a notebook user, I want a clearly organized, reproducible notebook, so that judges and future developers can follow the logic and re-run it from top to bottom.

#### Acceptance Criteria

1. THE Notebook SHALL be structured with clearly labeled Markdown heading cells for each of the following sections in order: (1) Setup & Imports, (2) Load & Validate Data, (3) Exploratory Data Analysis, (4) Feature Engineering, (5) Train/Validation/Test Split, (6) Model Training, (7) Threshold Tuning, (8) SHAP Explainability, (9) Policy Engine, (10) Demo Validation.
2. THE Notebook SHALL fix all random seeds (Python `random`, `numpy`, LightGBM `random_state`) to `42` in the Setup cell.
3. THE Notebook SHALL be fully executable from top to bottom in a clean kernel without manual intervention.
4. THE Notebook SHALL NOT contain any cell that requires internet access at runtime.
5. THE Notebook SHALL import all third-party libraries in the first code cell and SHALL NOT introduce new imports in later cells.
6. THE Notebook SHALL print library versions for `pandas`, `numpy`, `lightgbm`, `shap`, `sklearn`, and `joblib` in the Setup cell to aid environment debugging.
